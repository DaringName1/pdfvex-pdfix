# Local certificate signing progress

This implements initial PDF approval signing with an explicitly selected local Windows RSA certificate/private-key provider. It is a working source implementation toward A02, with syntax/native compilation completed and runtime acceptance pending. It does not claim complete Acrobat, PAdES, certification, multiple-signature, trust-service or legal-signature equivalence.

## Supported flow

1. Inspect the immutable opened source inside the fixed document AppContainer. Require a complete PDF/security/signature inventory, a single classic-xref revision, no encryption, no existing signature fields/dictionaries, and no certification, field locks, seed constraints, usage-rights permissions or XFA. Cross-reference subsections, object identities/offsets, complete inventory, Root and Size are checked before adding a revision. Xref streams, hybrid files and historical incremental sources are explicitly unsupported in this first slice.
2. Enumerate RSA certificates from Windows `CurrentUser/My` read-only, including certificate subject, issuer, serial, fingerprint, validity dates, RSA key size and registered key-provider name. Only provider metadata and the public certificate are read during enumeration; private-key handles are not acquired. Expired/not-yet-valid certificates or restrictive key usage remain visible but cannot be selected for signing. The user must choose a certificate and review its details and the document before the Sign action.
3. Prepare a new incremental revision inside the document engine. Every original source byte remains an exact prefix. New indirect objects contain the approval signature, an invisible AcroForm signature field, an updated form and a new catalog. The appended classic xref and trailer point to the prior revision with `/Prev`, retaining `/Info` and `/ID`. The signature uses `/Filter /Adobe.PPKLite`, `/SubFilter /adbe.pkcs7.detached`, a fixed-width `/ByteRange` and a 32 KiB hex `/Contents` reservation. Reason and location are UTF-16 PDF hex strings. No original page streams, keys or source file are rewritten.
4. Parent validation checks the original prefix hash, complete output hash, exact excluded Contents framing, all-zero reservation, full-file ByteRange, selected certificate fingerprint, reviewed metadata and SHA-256 over the exact covered bytes. CMS signed attributes are fixed canonical DER containing only `content-type=id-data` and `message-digest=SHA-256(covered bytes)`; the parent reconstructs all 77 attribute bytes rather than trusting a document-provided signing request.
5. Only the explicit Sign action launches `CertificateSigning.cs` with the fixed `sign-v1` protocol. It receives the selected certificate ID/provider and bounded hashes/signed attributes, never PDF bytes, paths, algorithms, commands or private-key material. It reopens the selected CurrentUser certificate, rechecks its dates, key usage, fingerprint and provider, reconstructs the signed attributes, and acquires a key handle with `CryptAcquireCertificatePrivateKey` using `ALLOW_NCRYPT`, `COMPARE_KEY` and `NO_HEALING`. Provider PIN/consent UI is allowed at this stage. RSA SHA-256 PKCS#1 v1.5 uses CNG `NCryptSignHash` or legacy CryptoAPI `CryptCreateHash`/`CryptSetHashParam`/`CryptSignHash`. CAPI little-endian signature bytes are reversed for CMS. The provider result is verified against the selected certificate's public key before return. No private key is exported or imported, and the code never requests a provider-specific key file.
6. The document engine assembles detached CMS SignedData using the selected leaf certificate and its exact issuer/serial, then fills only the reserved Contents bytes. It independently reopens the full new PDF through the existing certificate inspection implementation, reparses CMS/ByteRange/Contents, and verifies the signature and signed digest over the actual output. The result must have exactly one source-bound signature covering the entire current file, with the selected signer fingerprint and expected signature object. Parent validation checks this receipt and independently compares covered-byte hashes before retaining a saveable output. Raw DER certificate bundles are removed from the renderer receipt.
7. The user saves the verified signed PDF as a new copy. The native service retains sealed output bytes and source/token bindings; renderer-provided arbitrary bytes are never used as the save source. Cancellation, source departure or discard invalidates the retained copy. Source fingerprint fencing and collision-safe copy saving are also enforced by the main-process integration.

## Provider and containment boundaries

The document parser and CMS authoring code run only in the fixed document AppContainer. The Windows certificate provider adapter runs with normal user certificate/key-provider access and is not a document parser. Registered CAPI/CNG smart-card, token and HSM providers can participate through their Windows handles when they support the requested RSA operation; a registered certificate does not establish connected hardware, PIN availability or successful signing. Provider-specific runtime compatibility remains untested. Unsupported provider behavior fails closed without a signature receipt.

The native helper accepts only fixed `list-v1` and `sign-v1` operations, reads bounded stdin, returns a SHA-256-bound response, and has no shell/path request surface. Certificates are bounded to 64 KiB, enumeration to 100 certificates and 1 MiB combined DER, requests to 16 KiB and output to 2 MiB. A one-process Windows job caps memory at 256 MiB and CPU time at 20 seconds. The parent allows 30 seconds for enumeration or two minutes for an explicit signing/PIN interaction, enforces output limits and waits for observed process exit. If termination is not observed within five seconds, the provider remains closed and no output is released. Provider UI or external vendor components may have their own lifecycle; physical-device and cancellation acceptance remain pending.

Executable SHA-256, strict manifest policy and an explicitly reviewed source SHA-256 pin are checked before launching the fixed helper. The build refuses a changed native source until the pin is updated. The selected certificate metadata and public DER are retained in main-process memory, so renderer input can select only a certificate from that inventory. Sign responses must match the exact reviewed certificate, source hash, prepared-copy hash, covered-content hash and signed attributes.

## Explicit limitations

- Only initial, invisible RSA 2048–8192-bit SHA-256 PKCS#1 v1.5 approval signatures are authored. ECDSA/RSA-PSS signing, visible signature appearances, certificate enrollment, certificate import, local key generation and key export are not implemented.
- Existing signatures and signature fields, prior incremental revisions, certification/DocMDP/FieldMDP, locks/seed constraints, encrypted documents and xref streams are refused. Supporting multiple signatures requires authenticated revision/modification-policy handling rather than weakening those checks.
- CMS includes the selected leaf certificate. Intermediate certificates are not downloaded or embedded; subsequent chain building can use separately available local Windows certificate material.
- Certificate identity displayed during selection is a certificate claim. Signing does not establish chain trust, revocation status, Adobe/EU trust-list membership, document-signing EKU/issuance policy, trusted signing time, long-term validation or legal status. No TSA, OCSP, CRL, credential, external account or cloud service is contacted by this implementation. Native third-party key providers can have their own configured behavior.
- Original bytes remain intact, but the new root/form and signature revision change the document structure. Parser interoperability, malformed-file differentials and preservation across real-world files require runtime acceptance. Existing restrictions remain deliberate until that work is authorized.

## Integration contract

- `PdfCertificateSigningService` from `desktop/pdf-certificate-signing-service.cjs` provides `inspect(sourceId,source)`, `listCertificates()`, `sign(sourceId,source,token,{certificateId,reason,location})`, `output(sourceId,source,token)`, `cancel`, `discard` and `dispose`. Its optional `signingHelperPath` is a fixed app-owned executable path, never renderer input.
- Fixed contained operations: `certificate-sign-inspect` with `{}` returns an inert report; `certificate-sign-prepare` with `{certificateDer,certificateFingerprint,reason,location}` returns `{bytes,report}`; `certificate-sign-finalize` with `{preparation,certificateDer,signature}` returns `{bytes,report}`. Codec exports are `inspect`, `prepare`, `finalize` in `desktop/pdf-certificate-signing-codec.cjs`.
- Renderer methods: `inspectPdfCertificateSigning(id)`, `listPdfSigningCertificates()`, `signPdfWithCertificate(id,token,selection)`, `savePdfCertificateSigning(id,token)`, `cancelPdfCertificateSigning(id,token)` and `discardPdfCertificateSigning(id,token)`. UI export: `showPdfCertificateSigning(file,{announce})`, returning a dialog with `prepareDeparture`.
- Build `buildCertificateSigningHelper()` from `scripts/build-certificate-signing-helper.mjs`; package `dist/native/certificate-signing/{PDFix.CertificateSigning.exe,manifest.json,NOTICE.txt}`. The manifest policy is `windows-local-rsa-signing-v1`, with the pinned source hash exported as `SOURCE_SHA256` by `desktop/certificate-signing-provider.cjs`.

## Validation performed and pending

JavaScript syntax checks and native C# compilation with warnings treated as errors passed. Per the user's instruction, no helper was executed, no local certificates/keys were enumerated or used, no PDF fixtures were loaded, and no device/PIN/runtime/UI tests were run. Mandatory follow-up acceptance includes actual Windows provider behavior, CAPI/CNG signature format, single-revision PDF interoperability, altered-source rejection, independent viewer validation, malformed input, cancellation during provider UI and original-file preservation.

## Primary references

- [RFC 5652](https://www.rfc-editor.org/rfc/rfc5652): detached CMS SignedData, issuer/serial signer identification, exact signed-attribute DER and signature verification.
- [Adobe PDF 1.7 reference](https://opensource.adobe.com/dc-acrobat-sdk-docs/pdfstandards/pdfreference1.7old.pdf): incremental updates, AcroForm signature fields, signature dictionaries, ByteRange and Contents.
- [Microsoft CryptAcquireCertificatePrivateKey](https://learn.microsoft.com/en-us/windows/win32/api/wincrypt/nf-wincrypt-cryptacquirecertificateprivatekey): certificate-bound CAPI/CNG acquisition, public-key comparison and provider UI behavior.
- [Microsoft NCryptSignHash](https://learn.microsoft.com/en-us/windows/win32/api/ncrypt/nf-ncrypt-ncryptsignhash): CNG provider signatures and PKCS#1 padding.
- [Microsoft CryptSignHashW](https://learn.microsoft.com/en-us/windows/win32/api/wincrypt/nf-wincrypt-cryptsignhashw): CryptoAPI signing and signature byte order.
- [Microsoft CryptSetHashParam](https://learn.microsoft.com/en-us/windows/win32/api/wincrypt/nf-wincrypt-cryptsethashparam): supplying an already-computed digest to the CryptoAPI hash object.
