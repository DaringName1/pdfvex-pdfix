# Existing tag-tree table and related semantics

Status: implemented in source, syntax checked only. Runtime, PDF fixtures, reader/assistive-technology behavior, cancellation and end-to-end saving remain unverified. No tests were created or executed for this workstream, as requested.

The existing tag-tree copy workflow now allows reviewed Table / TR / TH / TD semantics, header Scope (Row, Column or Both), explicit Headers associations and RowSpan / ColSpan values. Header identifiers can be explicitly authored or removed. The UI can assign a header identifier and lists only identified TH candidates from the same containing table. These are actual writer mutations and reopened inventory checks, not an inspector-only draft. Existing attributed TH and TD roles can be corrected when their sole attribute owner is Table; incompatible surviving Scope values are refused.

Identifier edits are limited to unambiguous existing table headers (or removal from a former header). IDs use bounded byte strings, are unique throughout the inventoried document and resolve through a checked name tree. An absent IDTree can be created. An existing supported tree is replaced through the root field with a sorted tree covering the staged element IDs; every old indirect IDTree object is retained unchanged. Existing entries must agree with the source element IDs. Extended, malformed, cyclic, duplicate, unordered or overlapping IDTree structures are explicitly refused. Changing an ID does not silently retarget existing Headers: any old references must be explicitly corrected in the same draft, or the build fails.

Touched tables require direct TR children or supported THead / TBody / TFoot groups, a maximum of one caption and one group of each kind, and TH / TD row children. The bounded grid accounts for spans and refuses overlapping cells, spans beyond the final row, holes/irregular widths and oversized grids. Header arrays must point uniquely to other TH cells in the same containing Table and match the IDTree; recursive header cycles are refused. Reordering table children checks the final grid/order. These checks establish structural consistency; they do not infer which header has the correct meaning or certify table accessibility.

ListNumbering can be edited on L tags with absent attributes or a single List owner. The supported PDF 1.7 values are None, Disc, Circle, Square, Decimal, UpperRoman, LowerRoman, UpperAlpha and LowerAlpha. Existing visible labels are preserved. Printable, noninteractive leaf Form tags can receive PrintField Role (rb / cb / pb / tv), lowercase checked (on / off / neutral) and Desc properties. A checked state requires rb or cb. Interactive/object references, nested Form structures, class attributes, revisioned attributes and multiple attribute owners are refused. Existing Link tags continue to support Alt and Lang corrections while their object references, destinations and actions remain unchanged. Source scripts/actions are never executed by tag authoring or page previews; PDF.js previews disable evaluation and XFA.

The trusted selection/result validators accept only the declared mutations and verify readback values, table membership and header identities. Receipts retain source, inventory, selection and output SHA bindings; the native-owned report is sealed again before saving. The writer preserves all original indirect objects, unselected tag fields, unknown keys inside the retained single-owner attribute dictionaries, streams, MCIDs, content ownership and page resources, then reopens the candidate and compares intended object fingerprints. Only the selected tag fields and the required root IDTree field may change. Original PDF bytes are retained by the copy workflow.

Cancellation now awaits native job settlement and fails explicitly if termination/cleanup was not observed. Preview discard/destroy operations are tracked and awaited before rebuilding or closing. A cleanup failure retains the departure guard and disables further building/saving rather than announcing successful cancellation. These lifecycle changes have only been source reviewed and syntax checked.

Still unavailable: automatic header inference, creating/moving/splitting/merging existing tree elements across parents, irregular or class/revision/multiple-owner table remediation, namespace/PDF 2.0 authoring, interactive field property changes, link destination edits in this workspace, semantic acceptance, and PDF/UA / Section 508 certification. Existing initial-tagging support and its separate limits are unchanged. This checkpoint supersedes the older statement in PDF-TAG-TREE-PROGRESS.md that header associations require preexisting identifiers/IDTree and that identifiers cannot be authored.

Attribute decisions were checked against the primary [ISO 32000-1:2008 specification hosted by Adobe](https://opensource.adobe.com/dc-acrobat-sdk-docs/standards/pdfstandards/pdf/PDF32000_2008.pdf), clause 14.8.5 and tables 347–349. Current PDF 2.0 differences were consulted in the [PDF Association structure attribute sheet](https://pdfa.org/download-area/cheat-sheets/StructureAttributes.pdf) and [published clause 14 errata](https://pdf-issues.pdfa.org/32000-2-2020/clause14.html); this writer continues to refuse PDF 2.0/namespace sources rather than downgrading them. Byte-string and reference construction was source reviewed against installed pdf-lib PDFHexString, PDFRef and PDFContext implementations.
