# Editable document workflows — source progress

The first editable workflow runner is coded for one selected original PDF. The user can add, remove, edit and move two kinds of stages: preserving physical-page reorder and Bates numbering. If both are present, the native desktop service runs them in the visible order. Each stage consumes the previous stage's checked PDF output. The first input is taken from the trusted opened source handle; renderer-provided PDF bytes are never accepted as a workflow input. The runner does not print, transmit, overwrite or automatically save anything.

The reorder stage invokes the existing contained page-order inspector and writer. It requires a complete permutation of the current physical pages and retains eligible comments, links, forms and page object identities under that service's contract. The Bates stage invokes the existing contained decoration writer, with 1–100 chosen current physical pages, exact ASCII prefix/suffix and fixed-width numbering. Moving Bates before reorder changes which original pages receive identifiers. Both stages retain their native source/output reports, and each report's hashes are checked against the actual intermediate bytes before the next stage starts. Intermediate bytes are kept in the desktop process and erased after use. Cancellation covers the full operation; unobserved containment cleanup closes the wrapper service.

The visible workspace edits both stages, shows progress, previews every actual output page beside its corresponding original page, displays the native step receipts, and requires viewing all output pages plus an explicit review checkbox before the native exclusive-copy save route can be called. Editing the steps invalidates the preview and its token. The save bridge must revalidate the original selected handle and native output after the filename picker; `DocumentWorkflowService.output(id,source,token)` performs that check and returns `{bytes,report}` with `report.sha256`. The service's `status()` supports the desktop status route. The renderer contract is `new DocumentWorkflowWorkspace(reader,{announce,onClosed}).open()` with `prepareDeparture()` and `close()` for source changes.

This is an initial F28 slice, not completion of the adopted editable-workflow scope. Native multi-PDF combine cannot currently feed this pipeline: the existing combine workspace constructs its copy in a renderer job, while the contained native engine exposes only single-source preserving reorder and decoration operations. The wider plan still includes trusted multi-source import/combination, more step families, durable named workflow definitions and recovery, richer progress, interrupted-run recovery, resumable receipts and broader document/action formats. No claim is made that Bates numbers are unique across files or absent from existing artwork; users must review those collisions.

Syntax checks were run on the four new JS/CJS files. Runtime, UI, PDF corpus, rendering, security, device and engine tests were not run. Compilation is the parent integration gate.
