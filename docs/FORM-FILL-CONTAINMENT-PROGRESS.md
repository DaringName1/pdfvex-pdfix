# Fill and sign containment migration

Status: implemented in source; runtime acceptance remains pending. No document execution, PDF parsing runs, UI runs, tests or fixtures were used during this migration.

The existing Fill and sign workspace uses `inspectPdfFormFill(id, token)` and `buildPdfFormFill(id, token, draft)` through the fixed native document engine operations `form-fill-inspect` and `form-fill-build`. There is no renderer PDF-worker inspection or fill-writing fallback. PDF.js remains responsible for original/output artwork review and comparison.

`desktop/form-fill-codec.cjs` is child-only and bundles the existing pure form writer. `desktop/form-fill-validation.cjs` validates inert inspection, draft and output receipts in the parent; it imports no PDF parser. `desktop/form-fill-service.cjs` binds accepted inspections and sealed copies to the opened source ID, SHA-256 and operation token. Native saving accepts only the ID/token and obtains the sealed bytes from the service, never renderer output bytes. The existing exclusive new-copy save route preserves the original.

Inspection refuses encrypted, certified/permission-controlled, signed, XFA, malformed, ambiguous and excessive structures. Nested dictionaries/references are bounded and checked for signature and protection markers. Source/output limits are 100 MiB, 500 pages, 500 fields and 2,000 visible field locations. Drafts retain their 2 MiB bound; the fixed build request allows 3 MiB for its envelope. Inert inspection/draft/report validation has a 200,000-node, depth-24 budget beneath the shared transport budget. Inspections and reports are bounded to 4 MiB. Output PDF bytes use the separate native binary slot; no embedded preview byte arrays are emitted.

The native writer recomputes the reviewed declarative calculations and rejects stale unapplied results. It preserves read-only, password, unsupported, rich-text/file-selector and document-calculated fields. Password values remain withheld from inspection, output receipts, field-data export and renderer recovery. Raw protected dictionaries used for preservation verification stay inside the child.

After saving in the child, the copy is independently reopened. Checks compare every expected field value and original field schema/protection/choice/location/action inventory, intended field/widget dictionaries and appearance stream payloads, original page stream references and bytes, crop/media boxes, rotation, annotation order, unrelated annotation dictionaries, untouched field dictionaries/appearances, original resource slots, and the exact generated page stream/resource payloads for typed, drawn and PNG placements. The inert receipt matches the canonical draft hash, changed field values, exact placement identities/geometry/content hashes, source hash and exact binary output hash. Native output seals are zeroed on discard, cancellation and disposal.

The workspace retains calculation review/apply, undo/redo, saved-signature opt-in, original/output comparison, supported field-data export, recovery retries/rescue copies and sensitive-value filtering. Native cancel and departure await the contained operation and observed cleanup; unsafe process-exit/cleanup state prevents departure. Editing invalidates the native seal. Renderer preview generations prevent canceled results from becoming savable.

Verification performed here: `node --check` for the new codec, validation and service plus the changed form workspace, pure form output and PDF worker. Whole-app compilation is coordinated by the parent after all source changes freeze. Runtime/PDF/UI acceptance has deliberately not been performed and must not be inferred from syntax checks or compilation.

Scope remains unchanged: visual signatures are page artwork, not certificate signatures. PDF scripts/actions are retained but not executed. This route does not sanitize a PDF, certify accessibility or validate a certificate signature.
