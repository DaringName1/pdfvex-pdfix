# Certificate signature validation progress

This implements a contained, read-only certificate inspection slice toward the full PDFix document workspace. It is not a claim of complete certificate, PAdES, signing, trust-service or specialist PDF support.

## Implemented

- The fixed `certificate-inspect` operation accepts only source PDF bytes and no paths, URLs or document-supplied operations. `PdfCertificateService` extends `ContainedServiceContext`; its inert output validator checks the original source SHA-256 and byte length. The original is never rewritten.
- A bounded lexical source walk skips comments, literal strings and length-delimited streams. It binds a unique indirect signature dictionary to the parsed PDF dictionary. Four direct ByteRange integers must begin at zero, remain in bounds and exclude exactly that dictionary's direct hexadecimal Contents token. The covered revision must terminate at EOF. Appended bytes are reported as uncovered; a previous-revision integrity result does not certify the current document.
- Detached `adbe.pkcs7.detached` and a restricted `ETSI.CAdES.detached` subset verify CMS SignedData, detached id-data, a unique signer certificate binding, signed message-digest and the cryptographic signature. Supported digests are SHA-256/384/512; algorithms are RSA PKCS#1 v1.5 with 2048–8192-bit keys, and ECDSA on P-256/P-384/P-521. Node's native crypto verifies signatures and reads X.509 certificates.
- Signed attributes use the exact encoded bytes with the IMPLICIT context tag replaced by SET per RFC 5652 section 5.4. Definite minimal DER lengths, bounded depth/nodes, SET order, single-valued unique attributes and the content-type/message-digest pair are required. Supported attributes are content-type, message-digest, signing-time and restricted signingCertificateV2. ESS certificate hash and optional exact issuer/serial bindings are checked. Unknown signed attributes are unsupported, never silently ignored.
- The modal displays signature integrity, byte coverage, signer certificate claims and fingerprint, claimed signing time, and current certificate date validity. The offline Windows certificate chain is a separate result, including the chain subjects, issuers, SHA-256 fingerprints, validity dates, Windows error flags and base-policy status. Trusted timestamps, revocation and document modification policy remain explicitly not checked. A trusted offline base chain never produces an overall "valid PDF signature" conclusion.
- Only signatures whose covered bytes and CMS signature passed integrity verification release a signer-first DER certificate bundle from the contained engine. Parent validation bounds each certificate to 64 KiB, each bundle to 128 KiB and 32 certificates, checks canonical base64 and complete DER outer framing, rejects duplicate certificate hashes, and binds the first DER certificate SHA-256 to the reported CMS signer. Internal reports are limited to 6 MiB. The contained source hash and byte length are checked before any native trust operation. Raw certificate bundles are removed before renderer IPC.
- `CertificateTrust.cs` accepts one fixed stdin protocol and a fixed operation argument, with no PDF bytes, file paths, URLs or arbitrary operations. Certificates must be single DER X.509 certificates; PKCS#12/key containers and other certificate-store encodings are refused. It creates an ephemeral memory store of supplied candidates, calls Windows `CertGetCertificateChain` at the current time, and runs `CERT_CHAIN_POLICY_BASE` without ignored errors. The supplied certificates are never added to the trusted root store. Trust additionally requires the final chain certificate SHA-256 to match an existing CurrentUser or LocalMachine Windows Root certificate, all chain/element errors and base-policy errors to be zero, all certificate dates to cover inspection time, and the signer key usage to permit digital signature or nonrepudiation when present.
- Offline behavior is explicit: `CERT_CHAIN_CACHE_ONLY_URL_RETRIEVAL`, `CERT_CHAIN_DISABLE_AUTH_ROOT_AUTO_UPDATE`, `CERT_CHAIN_DISABLE_AIA` and `CERT_CHAIN_REVOCATION_CHECK_CACHE_ONLY` are set; no revocation-check or peer-trust flag is enabled. Local Windows stores and cached chain material are consulted; the adapter never downloads issuer certificates, CRLs, OCSP, trust lists or roots, and never modifies certificate stores. Locally installed enterprise or user roots are eligible, so a passing result describes this computer's trust configuration, not Adobe/EU trust-list membership or universal identity assurance.
- The native helper has a one-process Windows job, 256 MiB memory and 15-second process CPU limit; its parent applies a 30-second wall-clock limit, bounded stdin/stdout, no shell, and hidden-window launch. Cancellation waits for observed exit. Failure to observe termination within five seconds permanently closes that service and withholds its result. The application checks a strict helper manifest, executable SHA-256 and a pinned source SHA-256 before launch. The build refuses changed native source until its explicit pin is reviewed and updated. The reply includes the exact request SHA-256, source SHA-256 and signer fingerprint; every result is shape-checked and recomputed for consistency before release.

## Conservative refusals and remaining work

Encrypted PDFs, direct/compressed signature dictionaries, repeated definitions of the signature object, indirect stream lengths, duplicate dictionary keys, malformed syntax, alternate signature subfilters, BER/indefinite encodings, unknown signed attributes, multiple CMS signers, unsupported keys/algorithms and ambiguous certificate bindings are reported as unsupported. Inventory includes parsed orphan signature objects; it does not assert that a signature field is active or visible. No historical object graph or DocMDP/FieldMDP permissions are validated. PDF parser differential analysis remains specialist work.

Remaining: application-managed trust anchors and Adobe/EU trust lists; document-signing EKU, issuance and signature-policy validation beyond the Windows base policy; offline and consented online OCSP/CRL paths; authenticated RFC 3161 timestamps and long-term validation evidence; broader CMS/PAdES/ESS and RSA-PSS support; certificate signing and hardware key integration; incremental revision policy analysis; specialist PDF encodings and additional standards. CTL-linked multiple-simple-chain paths are conservatively unavailable. Expired or not-yet-valid certificates fail current-time chain validation even if signature mathematics pass; signer-claimed signing time is never used to backdate trust. No document-supplied URL, certificate AIA URL, CRL location, arbitrary file or external executable is accessed.

## Source checks and integration

Runtime, PDF fixture and UI tests are intentionally not run in this coding pass, per the user's instruction. JavaScript syntax checks and native compilation with warnings treated as errors passed. No PDF or native helper runtime was invoked. This parser/verifier and offline chain adapter have not been runtime-tested; cryptographic interoperability, native structure marshalling, trusted/untrusted/expired/tampered fixtures, malicious DER, offline network observation, cancellation and adversarial acceptance remain explicit validation tasks before production certification.

Integration contract: `inspect` from `desktop/pdf-certificate-codec.cjs`; `PdfCertificateService.inspect(sourceId,source)` where source retains the opened fingerprint; register `certificate-inspect` with empty options only in fixed engine/native allowlists. Bridge `inspectPdfCertificates(id)` and `cancelPdfCertificates(id)`, fence fingerprint after await in native IPC, dispose/cancel with other contained services. UI exports `showPdfCertificateReport(file,{announce})` from `src/pdf-certificate-workspace.js`.

Offline chain integration: build `buildCertificateTrustHelper()` from `scripts/build-certificate-trust-helper.mjs` and package `dist/native/certificate-trust/{PDFix.CertificateTrust.exe,manifest.json,NOTICE.txt}`. Pass the app-owned packaged executable as `trustHelperPath` in `PdfCertificateService` options; its development default points to that dist directory. No new renderer method or renderer-supplied path is accepted. Contained validators must use `validCertificateReport(...,{internal:true})`; final reports use the default validator with null bundles and optional validated `chainInspection`. `trust` is `not-checked`, `unavailable`, `trusted-offline-chain` or `untrusted-chain`. Helper unavailability preserves the separate contained integrity result and makes no trust claim.

## Primary references

- [RFC 5652, sections 5.3–5.6 and 11](https://www.rfc-editor.org/rfc/rfc5652): CMS signer identifiers, digest/signature verification and exact signed-attribute input.
- [RFC 5754](https://www.rfc-editor.org/rfc/rfc5754): SHA-2 CMS algorithm identifiers.
- [RFC 5753](https://www.rfc-editor.org/rfc/rfc5753): ECDSA CMS algorithm identifiers.
- [RFC 5035](https://www.rfc-editor.org/rfc/rfc5035): ESS signingCertificateV2 binding.
- [Node.js crypto API](https://nodejs.org/api/crypto.html): X509Certificate, createVerify, explicit RSA padding and DER ECDSA signatures.
- [Adobe PDF reference archive](https://opensource.adobe.com/dc-acrobat-sdk-docs/pdfstandards/pdfreference1.7old.pdf): signature dictionaries, Contents and ByteRange.
- [Microsoft CertGetCertificateChain](https://learn.microsoft.com/en-us/windows/win32/api/wincrypt/nf-wincrypt-certgetcertificatechain): explicit offline URL/AIA/root-update controls and Windows chain building.
- [Microsoft CertVerifyCertificateChainPolicy](https://learn.microsoft.com/en-us/windows/win32/api/wincrypt/nf-wincrypt-certverifycertificatechainpolicy): base-chain policy checks and policy status.
- [Microsoft CERT_TRUST_STATUS](https://learn.microsoft.com/en-us/windows/win32/api/wincrypt/ns-wincrypt-cert_trust_status): chain errors, time validity, untrusted roots and explicit distrust.
- [Microsoft CERT_CHAIN_CONTEXT](https://learn.microsoft.com/en-us/windows/win32/api/wincrypt/ns-wincrypt-cert_chain_context), [CERT_SIMPLE_CHAIN](https://learn.microsoft.com/en-us/windows/win32/api/wincrypt/ns-wincrypt-cert_simple_chain), [CERT_CHAIN_ELEMENT](https://learn.microsoft.com/en-us/windows/win32/api/wincrypt/ns-wincrypt-cert_chain_element), and [CERT_CHAIN_PARA](https://learn.microsoft.com/en-us/windows/win32/api/wincrypt/ns-wincrypt-cert_chain_para): native structure contracts.
