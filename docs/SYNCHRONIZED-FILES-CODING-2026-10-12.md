# Synchronized-file availability — October 12, 2026

F53 now has a real native selection/inspection/review/open workspace and a command-finder action. It uses folders already synchronized by the user's installed provider; it does not configure accounts, purchase a service or grant a whole folder. A fixed hidden metadata broker receives a chosen path as JSON, checks Windows offline/recall/pin/network attributes, and reports the exact source, size and hard-link alias presence before opening. The renderer receives a short-lived opaque selection token. Source identity is rechecked after review; opening first waits for the current editor's departure/recovery handling.

The central FileStore opening hook also checks availability for normal picks, drops, recent-file reopen and other FileStore routes. Windows recall/offline flags cause a deliberate native download/open choice unless already approved in the synchronized-file dialog. Actual reading is delegated to Windows and the installed provider. FileStore retains stable immutable local source bytes or the existing disk-backed private snapshot. Regular file hard-link aliases can be read through the selected source; original aliases are never rewritten. Watched/search folder rules remain separately stricter and do not silently hydrate placeholders.

Offline/provider, missing source, lock/permission and network-backed errors now include a useful next step. Saved copies still use exclusive local-byte verification; provider upload completion, remote versions/conflicts and synchronization are outside that local proof. Large-source “Save a copy” now opens the bounded exact-copy workflow instead of being disabled. Whole-file editing/transforming limits remain separately disclosed.

Remaining: actual Google Drive/OneDrive/Dropbox placeholders, download cancellation and long-running provider timeouts, reparse-tag-specific provider adapters, hydration progress, changed-source/lock/alias/network/device/corpus/security/UI cases and remote conflict handling. No cloud-provider runtime compatibility is certified by compiling this route.

Windows hydration policy lets the installed synchronization provider supply data on access; this implementation infers a need for a reviewed download from reported availability flags, not from a claimed provider identity. See [Microsoft hydration policies](https://learn.microsoft.com/en-us/windows/win32/api/cfapi/ns-cfapi-cf_sync_policies) and [reparse point tags](https://learn.microsoft.com/en-us/windows/win32/fileio/reparse-point-tags). No explicit CfHydratePlaceholder integration is claimed.
