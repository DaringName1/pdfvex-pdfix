You are the lead product engineer for a Windows-first document app with the working name **Forma**. Plan the complete product and build it in tested stages.

## Product goal

Create one approachable app for opening, reading, fixing, editing, converting, and understanding common files. Users should be able to connect the AI models or agents they choose.

The app should solve frustrating document problems with clear, guided actions. It does not need to copy Adobe Acrobat or match every feature other document apps have.

## Design direction

Use the attached mockup as a starting point. If it is unavailable, follow this description:

- The home screen asks, “What would you like to do?”
- Users can open or drop a file, choose a common task, or reopen a recent file.
- PDF reading should use familiar controls such as page thumbnails, page navigation, zoom, search, and markup.
- Editing text documents should feel familiar to Word or Google Docs, with a page and simple formatting controls.
- Keep the visual design calm, clear, and uncluttered. Do not reproduce Adobe branding or its crowded interface.
- Prefer plain-language actions such as “Make this scan searchable” and “Make this file smaller.”
- Make it clear what users can do with each file type: **Open, Preview, Edit, Convert**.

## First: inspect and plan the whole product

1. Inspect the current workspace, its project instructions, existing code, and the mockup.
2. Preserve useful existing work. Do not replace a project structure without a good reason.
3. Decide on a practical architecture for a Windows-first desktop app. Consider security, document rendering, local processing, extensibility, packaging, and maintenance. Use current, maintained libraries and check their licenses.
4. Create these project documents:
   - `PRODUCT-PLAN.md` — users, problems solved, product principles, feature scope, and acceptance criteria.
   - `ARCHITECTURE.md` — app structure, major libraries, data flow, security boundaries, and extension points.
   - `FORMAT-SUPPORT.md` — a table of formats and verified Open/Preview/Edit/Convert capabilities.
   - `ROADMAP.md` — ordered phases, dependencies, and completion criteria.
   - `DECISIONS.md` — important assumptions and choices with brief reasons.
5. Then begin implementation. Do not stop after making the plan.

Do not ask me to approve routine implementation choices. Make sensible reversible choices, record assumptions, and continue. Pause only if blocked by missing credentials, a paid service decision, a destructive action, or another decision only I can make.

## Product areas to plan and implement

### 1. File workspace

- Open files with a picker or drag and drop.
- Show recent files, favorites, and file search.
- Keep the original file safe by default. Prefer saving edited or converted results as a new copy.
- Provide clear errors for unsupported, damaged, password-protected, or oversized files.
- Do not claim a format is fully editable if it is only previewable or convertible.

### 2. PDF reading and work

Build the reliable everyday PDF workflow:

- Render pages, show page thumbnails, navigate by page, zoom, search selectable text, and print.
- Add highlight, underline, notes, comments, drawing, and text annotations.
- Fill supported forms and add a saved signature.
- Insert, remove, reorder, rotate, extract, combine, and split pages.
- Compress PDFs with a preview of the quality and size tradeoff.
- Add password protection or remove it only when the user has the password and permission.
- Create PDFs from supported documents and images.

### 3. Guided fixes for common PDF problems

Make frequent problems easy to recognize and fix:

- Detect image-only scans and offer local OCR to make them searchable.
- Let users review OCR text and correct recognition mistakes.
- Preview conversions and warn about possible font, table, layout, or page-break changes.
- Make redaction permanently remove the selected content from the output. Verify the redacted text or image cannot be recovered through search or copy.
- Offer readable layouts, copy-text actions, and clear page references for long or awkward documents.
- Help users search one file or selected files.

### 4. Editing and converting other documents

Plan a useful format roadmap rather than claiming support for every file type.

Start by evaluating reliable support for:

- PDF
- DOCX, RTF, TXT, Markdown
- JSON, XML, YAML, CSV
- PNG, JPG/JPEG, TIFF, WEBP, HEIC/HEIF
- XLSX and PPTX preview or conversion

Research and test possible support for:

- Older DOC, XLS, and PPT files
- Apple Pages, Numbers, and Keynote files
- Other useful older or less common image/document formats

For proprietary or difficult formats, be honest: show whether the app can preview, import, edit, or convert them, and warn about formatting limits before conversion. Add formats only when the results are dependable.

Use a familiar Word/Docs-style editing experience for supported text documents. Include basic formatting, headings, lists, undo/redo, and save/export. Do not try to recreate a full office suite in the first release.

### 5. Choose-your-own AI and agent connections

Keep model providers and agent runtimes as separate connection types.

- Support local models and configurable OpenAI-compatible endpoints.
- Provide setup instructions, a connection test, model selection, and a way to remove a connection.
- Support Hermes Agent through its documented API where available.
- Keep a generic adapter design for other agents, including Harness where its documented interface permits.
- Let users select exactly which files are included in each AI conversation.
- Show the chosen provider and whether the files will remain local or be sent online.
- Ask before sending local files to a remote service.
- Let AI answers cite PDF page numbers or source lines.
- AI may explain, search, summarize, compare, or extract information. It must not edit, overwrite, or export a file without the user’s approval.
- Store credentials securely. Never put secrets in source code, logs, or exported project files.

### 6. Privacy, accessibility, and reliability

- Keep file processing local by default when practical.
- Use explicit permission before remote processing or broad agent file access.
- Use safe handling for untrusted document files and isolate risky parsing where practical.
- Support keyboard navigation, readable contrast, scalable text, and clear focus states.
- Include autosave or recovery where appropriate.
- Give clear progress indicators for OCR, conversion, and large-file work.
- Do not bypass DRM or passwords.
- Make errors actionable: explain the issue and offer a realistic next step.

## Build phases

Plan all phases up front, then implement in this order:

1. **Foundation:** app shell, file opening, recent files, support matrix, mockup-inspired home screen.
2. **PDF reading:** reliable rendering, page navigation/thumbnails, zoom, search, and print.
3. **PDF fixes:** OCR, page organization, compression preview, annotations, safe redaction, and save-a-copy flow.
4. **Documents and images:** supported previews, a basic Word/Docs-style editor for suitable formats, and dependable common conversions.
5. **AI connections:** local/custom endpoint setup, selected-file context, source references, and consent before remote sharing.
6. **Compatibility and polish:** Apple and older formats where feasible, accessibility, packaging, recovery, and usability fixes.
7. **Release readiness:** security review, licensing review, installation instructions, and a verified support matrix.

You may adjust the order if a dependency requires it, but record why. Complete and verify one phase before starting the next. Do not label planned or mocked features as complete.
