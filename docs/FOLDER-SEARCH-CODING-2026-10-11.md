# F58 / R48 folder search coding — October 11, 2026

Status: coded expansion of selected-file search; partial target, not accepted or release-ready.

The existing search dialog now offers an explicit native **Choose PDF folder** action. The user reviews PDF-only selectable-text search, recursion (unchecked initially), and session-only access before the picker. The resulting dialog shows the selected absolute folder and scope. Search grants do not imply editing, watching, recipes or saved indexing. Clear search revokes access and removes match excerpts, file metadata and retained buffers; closing, renderer teardown and the existing expiry also revoke grants. No new persistent index or consent store is created. Persistence is deliberately unsupported and the IPC rejects other purposes, file types and persistence values.

Folder discovery returns a session token immediately and runs asynchronously. The renderer polls bounded metadata/progress, allows Stop, and retains the discovered subset when enumeration is canceled. Limits are 1,000 PDFs, 20,000 directory entries, 2,000 directories, 32 subfolder levels and two minutes. Files/errors within those bounds are returned, with explicit partial/skipped reports. Error details are capped at 500 rows; the skipped counter continues. Sequential search makes one independently checked snapshot at a time, retains at most one native PDF buffer, and releases it after extraction. No folder-wide PDF buffer or extracted-text cache is assembled. Match snippets and source fingerprints stay in memory until clear/close/expiry. Search snapshots can involve transient native allocation, IPC and parser copies; this is bounded per file, not a claim of a single physical byte copy.

The new fixed Windows attributes broker reads no PDF content. User paths are JSON stdin values, not PowerShell script interpolation. It uses GetFileAttributes to reject all reparse points (including junctions, links and cloud placeholders), offline and recall flags, and network drives. It fails closed when that broker is unavailable. All ancestors are checked, real paths must match lexical paths and remain inside the selected root, PDF hardlinks are rejected, and discovered file identity/size/timestamps are checked before and after snapshot reads. Changed, missing, inaccessible, excessive-size, protected, malformed and extraction-failed PDFs have visible reports. Originals are fingerprint-checked before opening a result. Strict rejection can exclude some synchronized folders even if their content is hydrated; it does not weaken containment to accommodate them.

Existing individual-file APIs remain compatible. Added native APIs are `selectFolder(path, options)`, `folderStatus(token)`, `cancelFolder(token)` and `release(token, id)`. Folder options are exactly `{recursive: boolean, purpose: 'search', persistence: 'session', fileTypes: ['pdf']}`. `bytes(token, id)` continues to return the existing payload for selected files and returns a promise for folder files. Folder discovery metadata has no hash until the first independently checked snapshot; the renderer verifies returned bytes against their SHA-256 before extraction. Existing native callers await the IPC result. A release during a folder read invalidates that read.

The existing PDF.js selected-text search path is reused with physical page references, permission/password handling, a 120-second per-file extraction deadline, 100 MB/500-page per-PDF bounds, 2,000 total matches, 32 MB total extracted text and 2 MB per extracted page/text segment. Scans need OCR; comments, metadata and attachments are omitted. A large folder can hit the combined text/match limit before every discovered PDF is searched. Opening a result uses the existing source-opening workspace handoff.

Remaining work and security limits:

- There is no persistent encrypted index, incremental reindexer, index export or independent history management. Every new query rereads/extracts selected folder PDFs; index deletion is represented by removing the session cache because no saved index exists.
- Existing search extraction uses PDF.js in the renderer's worker architecture. It is not the native AppContainer PDF service. This change introduces no new PDF parser, but it does not prove OS containment, worker memory ceilings or native sandbox parity for this existing path. Broader parser containment remains unresolved.
- Path ancestry/realpath/stat checks detect ordinary link and file replacement changes. They do not establish a native handle-relative, deny-delete directory lease. A hostile directory/reparse replacement between a check and a filesystem operation remains an acceptance gap, including the existing `FileStore.open` handoff. The feature must not be described as having proved race-free grant containment.
- PDFs over 100 MB or 500 pages are visibly skipped; disk-backed whole-folder large-PDF search and OCR indexing are not implemented.
- Stop returns after any outstanding filesystem/attributes request completes (attributes request timeout is ten seconds). Extraction cancellation terminates the current existing PDF.js task and cancels/releases the native per-file read. No directory watcher is installed.
- No hundreds-file throughput, hostile junction race, cloud-sync, cancellation, renderer teardown, memory-pressure, permission-restriction or packaged-Windows acceptance run was performed for this coding pass. Root integration/build is separate evidence.

Validation: native search modules and renderer module parsed successfully with Node's module parser. An initial ad hoc syntax harness incorrectly parsed `import.meta` as a script; the corrected module-parser harness passed. No broad test suite was added or run.
