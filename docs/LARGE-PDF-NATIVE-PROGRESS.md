# Large PDF native loading

Implemented in `desktop/file-store.cjs` and `desktop/large-pdf-store.cjs`.

- The existing byte-packet path remains for sources at or below 100 MiB. Non-PDF opening, native editing/conversion, and output validation retain their 100 MiB limits. An explicit `open(..., {maxBytes})` remains a hard opening cap.
- Default PDF opening above 100 MiB attempts a disk snapshot up to the current 1 GiB viewer resource ceiling. Failure messages identify the viewer budget, RAM shortage, disk shortage, changed input, invalid header, or inaccessible storage. They do not describe the large-PDF reading ceiling as a 100 MB limit.
- RAM admission estimates `3 * PDF length + 256 MiB` for viewer work and leaves another 512 MiB for the operating system. The required available-memory threshold is therefore `3 * PDF length + 768 MiB`, compared with `os.freemem()` at admission. This estimate cannot guarantee successful rendering of complex PDFs.
- The bundled PDF.js range viewer still reserves a full-length byte array. Native range loading removes full-file native/IPC copies; it does **not** make total viewer RAM independent of document length.
- Where `fs.statfs` is supported, disk admission requires PDF length plus 64 MiB of headroom on the application-folder volume. Unsupported filesystem-statistics platforms still get bounded copying and a disk/permissions explanation on failure.
- A held original descriptor is copied and SHA-256 hashed sequentially using a 256 KiB buffer into an exclusive, random file in an app-owned temporary directory. Only the first 1,024 bytes are sniffed for `%PDF-`; no PDF parser or engine runs in this native path. Source descriptor size/device/inode/modified/changed times are fenced before and after copying, and an extra-byte probe rejects growth.
- The completed snapshot is made read-only, reopened read-only, and retained behind the opaque source ID. Snapshot paths and descriptors never appear in range IPC. Successful opening returns metadata with `rangeSource: {length, chunkSize: 262144}`, `largeFile: true`, a slower-reading notice, and reading-only capability metadata.
- `readPdfRange(id, begin, end)` accepts only safe integer, nonempty, in-bounds ranges of at most 1 MiB. It reads the retained snapshot descriptor exactly and fences both descriptor and snapshot-path metadata before and after the read. Missing, replaced, mutated, or ended snapshots cannot continue serving ranges.
- File-backed sources preserve metadata, fingerprint, reading-position, and source-check access. Their `bytes` getter throws `FileError` with `LARGE_PDF_OPERATION` and explains the existing 100 MiB per-operation editing/export limit. Copy and split saving also reject file-backed sources.
- Opening, reading ranges, releasing, clearing, and disposal use one serialized session queue. Retained sessions are capped at ten; their in-memory source bytes remain capped at 100 MiB, excluding disk snapshots. Normal opening clears prior sources only when the replacement is ready.
- `release(id)` closes and unlinks only the app-owned snapshot associated with that ID. `clearSessions()` immediately invalidates the open generation, then serializes cleanup while leaving the store usable by a replacement renderer. Snapshot copying checks cancellation between chunks. `dispose()` invalidates the generation permanently and closes/removes all tracked snapshots. Failed-open temporary files are removed; failed removals remain privately tracked for disposal retry and yield explicit cleanup errors. Abrupt OS/process termination cannot execute asynchronous disposal.
- Each snapshot root has an immutable, synced `snapshot-owner.json` marker containing exactly the application owner, version, UUID, and matching root leaf. The marker is durable before any UUID PDF file is created; it never needs a mutable file-list update that could be torn by process termination. The current store tracks exact owned UUID file leaves privately. On startup, `LargePdfStore.init()` scans only immediate matching roots, skips the active store root, reads ownership markers with a 16 KiB bound and descriptor/path stat fences, and derives a list of at most 128 regular UUID PDF leaves. Roots containing unrecognized leaves, links, or invalid markers are left untouched. Known cleanup revalidates root, marker, and leaf identity before each exact unlink, then removes the marker and empty directory; it never deletes recursively. Cleanup failure or invalid/torn marker warnings are exposed through `snapshotCleanupWarning` and the existing `recoveryWarning` without interrupting recent-file history loading. The application must hold its single-instance lock before initializing this cleanup.
- A trusted optional `store.onOpenProgress(event)` callback receives `{stage, name, size, bytes, total}` for large opening. Stages are `preparing`, `progress` (approximately every 500 ms while copying), `done` after the session commits, and `canceled` when opening fails or is invalidated. Callback exceptions and promise rejections are ignored; progress never reveals native snapshot paths or descriptors.

Validation in this change is limited to static inspection and `node --check` for both native source files. No app, runtime behavior test, PDF engine, or document fixture was executed.
