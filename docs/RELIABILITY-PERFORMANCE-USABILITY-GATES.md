# Reliability, performance, and workspace release gates

These are the user's top release priorities for PDFix. They govern the existing full product scope and free-app requirement; they do not remove previously adopted capabilities or establish a release date. “Never corrupt” and “100% bug-free” are product goals, not guarantees that software can prove. Release decisions require executed evidence on real files and supported hardware. Source compilation alone establishes neither output integrity nor runtime performance.

## Acceptance matrix — planned, not yet passed

| Priority | Release acceptance to measure | Failure rule and evidence |
| --- | --- | --- |
| Original and output preservation | For every save, sign, split, redact, page rewrite, and drawing measurement export route, hash the original before/after; create a separate output; verify saved disk bytes match reviewed bytes; independently reopen every resulting file. Exercise valid, malformed, encrypted, signed, interrupted, cancelled, out-of-space, and permission-denied inputs within each route's supported boundary. | A mismatch, unreadable output, unsupported structure, partial save, or unverified result is a failed operation. Keep the original unchanged, clean temporary output, and give a specific error. Do not report success from a writer callback alone. Record input/output hashes, independent reader results, and failure-path observations. |
| Signing and redaction correctness | For visual signatures, verify appearance and placement after independent reopen; for certificate signatures, verify cryptographic status, trust result, byte range, and any post-sign change under the supported policy. For redaction, inspect text extraction, page pixels, objects/streams, metadata, annotations, attachments, and saved bytes; verify every affected page and disclose flattening or other losses. | Fail closed if the chosen signing or redaction mode cannot prove its stated result. Do not call a visual signature a certificate signature. Do not call cropping or a black overlay redaction. Record independent validation and negative controls. |
| Blueprint precision | On representative engineering sheets, compare geometry, scale, calibration, rotated/cropped coordinates, markups, measurements, takeoff totals, and exported/reopened results against known reference values. Define per-tool tolerances in physical units and pixels before acceptance; test edge cases and calibration changes. | Refuse or clearly disable measurements when page scale/units are unknown or inconsistent. No invented precision. Log reference values, observed error, calibration state, and output round trips. |
| Large-document responsiveness | On a documented realistic Windows hardware tier, use real 500-page PDFs and 300 MB PDF/drawing sets. Record cold open, first useful page, page jump, scroll, zoom, search, thumbnail navigation, memory peak, cancellation, and sustained interaction over repeated sessions. Set numeric p50/p95 targets from baseline measurements before release and compare regressions against them. | No unbounded render/text/thumbnail work for the entire set on opening. Keep only a bounded visible-page window and nearby prefetch in active memory, cancel stale work, and recover from resource pressure without losing edits. Record hardware, corpus, timing traces, peak memory, and crash/hang results. |
| Workspace clarity | Drawing, Document, and Pages have separate primary workspaces with task-specific tools and clear return paths. Observe first-time and keyboard/screen-reader users completing representative drawing review, document editing, and page organization tasks. Measure task completion, wrong-workspace starts, backtracking, and time to the intended tool; set targets after baseline observation. | Fix unclear routing, hidden controls, focus traps, and repeated cross-workspace detours before release. Use contextual tools and short explanations; avoid banners or controls that crowd the document. Record task scripts and observation results. |

## Execution order and pending beta gates

1. Inventory every writer/output path and its failure modes. Apply fail-closed new-copy saving, original preservation, independent reopening, and mode-specific validation to each route. Include interrupted/cancelled operations and incomplete disk writes.
2. Build a real-file corpus for documents, difficult PDFs, drawing sheets, signatures, and redactions. Define expected visual/structural outcomes and engineering tolerances before running acceptance.
3. Measure the 500-page/300 MB scenarios on a named realistic hardware tier. Use traces to choose numeric interaction and memory budgets; then implement and verify bounded visible-page virtualization, cancellation, and regression limits.
4. Evaluate Drawing, Document, and Pages with representative users and assistive technology. Keep the main actions task-specific and discoverable while preserving all planned features in appropriate workspaces.
5. Release beta only after the applicable integrity, security, corpus, performance, accessibility, installation, and usability gates have executed and passed. Record known limitations against the supported format matrix. A source build, a single fixture, or a successful preview cannot close these gates.

The current coding pass does not execute runtime, UI, PDF, hardware, or corpus tests. Every acceptance row above remains pending until those checks are performed and recorded.
