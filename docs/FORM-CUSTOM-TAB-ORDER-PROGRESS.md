# Reviewed custom AcroForm keyboard order — October 9, 2026

Implemented in source inside the existing Fill and sign workspace. A page selector inventories the source's tab-order declaration and shows explicit reasons when a page cannot be reordered. Users select individual widget references, move them earlier/later, inspect an ordered list with PDF-coordinate locations and matching numbered rectangles on the page, check a review box, and apply the page order. Applied orders participate in undo/redo, reset, source-bound recovery, output invalidation, preview, comparison and the existing exclusive new-copy save. Pending unreviewed list moves are not written to the draft or PDF.

The existing fixed `form-fill-inspect` / `form-fill-build` engine operations carry the additional inert inventory, optional `tabOrders` draft property and verified output receipt. No new IPC route or renderer PDF writer was added. Missing `tabOrders` in older drafts defaults to an empty list. Each reviewed order contains the exact source SHA-256, zero-based page and complete permutation of stable indirect widget identities; restoration and native build reject stale or unsupported page identities. The shared recovery store continues to bind drafts to its source fingerprint and size bounds; form-fill parent validation and renderer restoration additionally validate the keyboard-order schema. The pure validator has a generated native counterpart produced by the existing model synchronization script. The native service retains source/token-bound output sealing, cancellation and original-preserving saving.

Supported pages contain at least two unique indirect, visible, supported editable AcroForm widgets and no other annotation types. Multiple widgets of one field are individually ordered by reference and rectangle. The complete page widget permutation is required: omissions, repetitions, unknown IDs, wrong pages, stale source hashes and unreviewed payloads are refused. Limits remain 100 MiB / 500 pages / 500 fields / 2,000 widgets, 2 MiB drafts and the existing 3 MiB build envelope. Inspection/report bounds remain 4 MiB.

Custom output replaces only the selected pages' annotation arrays and tab-order declarations, with `/Tabs /A`, and upgrades the copy's document catalog `/Version` to `/2.0`. The writer's PDF 1.7 file header can remain: catalog Version is the standards-defined version-upgrade mechanism. The Adobe-hosted [ISO 32000-2 FDIS, Table 31](https://developer.adobe.com/document-services/docs/assets/5b15559b96303194340b99820d3a70fa/PDF_ISO_32000-2.pdf) defines `A` as annotation-array order beginning with PDF 2.0. The current [ISO 32000-2:2020 errata, 7.5.2 and 7.7.2](https://pdf-issues.pdfa.org/32000-2-2020/clause07.html) clarifies that catalog Version can upgrade the current document version considering both its header and existing catalog declaration. These references establish the encoding; they do not establish any particular viewer's behavior.

The child independently reopens the output and verifies the requested widget permutation, `/Tabs /A`, `/Version /2.0`, exact retained widget/field dictionaries and appearances, complete annotation membership, untouched page order declarations, catalog entries other than the intended version, original artwork streams/resources, geometry and the existing value/overlay checks. Parent-side inert validation compares the exact reviewed source-bound orders and canonical draft hash to the receipt. No document script or PDF action is executed or installed.

Tagged/structure-ordered pages, mixed widgets and links/comments, direct/shared/orphaned widgets, hidden/out-of-view/protected/unsupported fields, widgets outside the crop/media intersection, ambiguous page associations and unsupported PDF-version declarations are refused for reordering. Existing encrypted/signed/certified/XFA form writing refusal remains. This feature does not edit tag trees, repair accessibility semantics, certify PDF/UA or PDF/A, or provide legacy PDF 1.x custom-order compatibility. Viewer interoperability, radio-group focus behavior and actual keyboard navigation require later acceptance work; older viewers may ignore PDF 2.0 annotation order. Existing scripts/actions are retained inertly as before.

Verification for this increment is syntax checking only, with whole-app/native codec compilation coordinated after source freeze. No runtime, PDF parsing execution, UI/device run, fixtures or new tests were used or added. Compilation is not runtime acceptance evidence. Broader forms work remains: script isolation/compatibility, declarative validation and formatting, full tagged-form navigation, mixed annotation navigation, non-Western appearance fonts and broader field/widget structures.
