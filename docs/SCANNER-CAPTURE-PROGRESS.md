## Implemented route

- A user opens Scan to PDF, enumerates Windows WIA scanners, explicitly selects one device, chooses flatbed or simplex feeder, 150/300/600 dpi and color/grayscale/black-and-white, then presses Scan. No native acquisition begins during startup or document opening.
- `desktop/native/ScannerCapture.cs` connects only the selected enumerated WIA scanner. It selects the WIA flatbed/feeder category; legacy WIA one-child trees use root document-handling source selection. WIA 2 feeders use `FRONT_ONLY` and `PAGES=1`; direct `Item.Transfer` repeats until the requested page limit or `WIA_ERROR_PAPER_EMPTY`. A flatbed page uses `CommonDialog.ShowTransfer`, allowing native progress/cancellation after the explicit Scan click. Repeated flatbed captures are retained as one pending renderer collection.
- The helper requests the universally supported WIA BMP transfer format, checks single-frame dimensions and collection pixel budgets, then normalizes with the Windows WIA `ImageProcess` Convert filter to PNG. The app checks actual PNG format, dimensions and frame count before accepting a page. This does not install or download a driver or launch a vendor program.
- `desktop/scanner-service.cjs` owns staging directories and a fixed executable path with a build-manifest SHA-256 pin. It passes only fixed operation names and validated device/settings arguments, using `spawn` with `shell:false`. It exposes opaque capture IDs and metadata, not arbitrary source/output paths or commands. Each captured PNG receives regular-file/path checks, signature/IHDR/chunk-framing/CRC/IEND checks, byte/pixel budgets, and a SHA-256 content fingerprint. Import rechecks fingerprints and PNG framing before returning bytes to the app-owned FileStore route.
- The native helper self-assigns a Windows Job object with a 768 MiB process memory limit, one-process limit and kill-on-close. Service enumeration has a 30-second deadline; capture has a 10-minute deadline. Cancellation terminates the owned helper, waits for observed process close, and completes output cleanup before settling the operation. Renderer destruction uses `disposeOwner`; service disposal and next initialization clean app-owned pending directories. Cleanup errors are reported, rather than represented as successful cleanup.
- Pending batches are limited to 10 pages total, 32 MiB and 16 million pixels (8192 pixels per side) per PNG, 100 MiB aggregate and 64 million pixels aggregate, matching the existing image collection. A page-limit result explicitly says more paper may remain. An empty feeder before the first image is an error. A cancellation, jam or failed capture discards the current batch's partial images while previously completed captures remain pending.
- The renderer can discard captures or import them to the existing image workspace. Parent integration saves scan PNG copies exclusively into a user-chosen durable folder and persists the collection so existing ordering, rotation, adjustments, reviewed PDF preview and exclusive Save PDF copy can operate. Original documents are untouched. Scanning does not add OCR/searchable text automatically.

## Integration contract

`createScannerService({root})` / `new ScannerService({root})`, where `root` is an absolute application-owned staging directory; call `await init()` before use. The default helper is `dist/native/scanner/PDFix.Scanner.exe`.

Methods:

- `listDevices(owner)` returns `{devices:[{id,name,manufacturer}],backend:'Windows WIA'}` and scopes the selected-device allowlist to that owner.
- `capture(owner,{deviceId,source,maxPages,dpi,color})` returns `{captureId,pages:[{id,name,ext:'png',byteLength,width,height,dpi}],completion}`. `source` is `flatbed` or `feeder`; flatbed requires `maxPages:1`, feeder accepts 1–10 within the remaining collection budget. Completion is `single-page`, `feeder-empty` or `page-limit`.
- `takeCapture(owner,captureId)` returns validated page records `{name,ext:'png',bytes,width,height,dpi}` for trusted FileStore staging. After staging and collection persistence succeed, call `releaseCapture(owner,captureId)`. Do not remove prior captures when FileStore staging fails.
- `releaseCapture(owner,captureId)`, `cancel(owner)`, `disposeOwner(owner)` and `dispose()` remove only owned, validated staging directories and files. No directory deletion follows a renderer-supplied path.

`ScannerWorkspace(root,{announce,beforeImport,onImported,setGuard})` exposes `open()`, `prepareDeparture()`, `releaseDeparture()` and `dispose({prepared})`. It expects narrow preload methods `scannerDevices()`, `scannerCapture(options)`, `scannerCancel()`, `scannerImport(captureIds)` and `scannerDiscard(captureIds)`. `beforeImport()` runs before native import to finish the current editor/drawing departure guard; returning false aborts import. Cancelled native directory/import selection retains captures and the caller restores its prepared editor state. `onImported(result)` runs after the scanner operation has finished, permitting navigation into the existing image workspace without waiting on its own active operation. A modal caller supplies `setGuard(value)` to compose pending scan/busy protection with the existing editor's guard; the standalone default calls `editorGuard(value)` directly. Import/discard IDs must be bounded, unique, owner-checked and serialized in the main-process integration. Handle import errors before releasing captures and restore application guards around navigation.

Build integration: call `buildScannerHelper()` from `scripts/build-scanner-helper.mjs` during Vite's native build stage. It uses the installed Framework64 C# compiler with `/platform:x64 /warnaserror+`, references Windows .NET libraries and outputs the executable, source/executable SHA-256 manifest and `NOTICE.txt` in `dist/native/scanner`. The Windows package builder must verify the scanner manifest/file hash and include it in its native inventory; its existing `dist` copy includes all scanner assets. Compilation does not launch the helper or touch a scanner.

## Trust and remaining limits

WIA acquisition and normalization execute in a full-user-access device helper outside the document AppContainer because driver/device access is needed. The helper's Job object limits its own process, not the out-of-process Windows WIA service or vendor driver. Windows/vendor image codecs run before PNG framing validation; a malicious or broken driver is outside document-parser containment. The app makes no HTTP requests or accepts network addresses/URLs in the scanner API; an explicitly selected installed WIA device may use its driver's own USB or network transport.

Image normalization/preview/PDF construction in the existing `ImageWorkspace` use browser WebWorkers in Electron's sandboxed, context-isolated renderer without Node integration. They are not the fixed native document AppContainer route. Main-process PNG checks validate framing and integrity, not compressed-pixel decoding or semantic artwork correctness. The image workspace independently previews/reopens the generated PDF and requires review before copy export; hardware quality, orientation, exact page region and silent driver truncation still require human inspection.

App cancellation observes helper exit and discards current outputs. It cannot promise that the physical feeder or Windows/vendor driver stops immediately; mechanical movement or a busy-device state can continue outside the helper. Native dialog handling, error recovery and driver teardown must be verified on real hardware. Driver-specific settings, automatic duplex, TWAIN-only devices, vendor-only protocols, arbitrary custom resolutions, hardware buttons and scanner fleet compatibility are not implemented. Current WIA automation source-tree/property support is an intentionally bounded compatibility route and may reject drivers that do not expose or honor the required settings. The scanner's default acquisition area is retained; cropping can be reviewed in the image workspace. A typical full A4/Letter page at 600 dpi exceeds the existing image-workspace 16-million-pixel limit and must be captured at lower dpi; the app rejects it transparently and does not silently downsize or change the requested resolution.
